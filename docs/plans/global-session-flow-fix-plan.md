# Global-session flow: audit + fix plan

**Status: all three tracks implemented.** Client, backend, and program crates
all compile clean. The Anchor program has **not been deployed to devnet
yet** — that's a separate, deliberate step (see "Implementation status"
below) since it touches the live program other people may be testing
against.

## Context

This session I wired the game client's create/join/delegate flow onto the
existing (but previously unused) **global session key** system, so a player
sees one wallet popup ever (authorizing the global session) instead of one
per game. That part works — verified against the actual on-chain account
structs, both crates compile clean.

While double-checking before the user tested it, I found that **move
recording breaks** for games created this way. A full audit (below) found
several more systems with the same root cause. This document explains what
was broken, why, and the fix that was implemented for each.

## Root cause

There are now two parallel ways a game gets created on-chain, and most of the
backend was only ever built for the first one:

| | Original flow | New global-session flow |
|---|---|---|
| Instructions | `create_game`/`join_game` + `authorize_session_key` | `global_create_game`/`global_join_game` only |
| Session key generated by | Backend | Client |
| Session key held by | Backend (`SessionStore`, keyed by `game_id`) | Client only (encrypted local file) |
| Per-game `SessionDelegation` PDA | Created by `authorize_session_key` | **Never created** |
| `GlobalSessionDelegation` PDA | N/A | Created once, per wallet, reused across games |

`authorize_session_key` is what the old flow uses to record, on-chain, "this
session pubkey may act for this game." The new flow deliberately skips it —
that's *how* it avoids the popup — but it means `game.fee_payer` is set to a
key that (a) no on-chain `SessionDelegation` account backs, and (b) the
backend has never heard of and cannot sign with.

Everything below is a consequence of one of those two facts.

Not currently called by the new flow's own code path, but anything else that hits these (e.g. a status UI) would break. |

One more gap I found reviewing my own change, not from the subagent: **my
delegation gating is wrong.** `handle_game_start_delegation` decides whether
to sign locally (global) or ask the VPS (old flow) by checking
`solana_state.global_session_active` — the wallet's *current* authorization
state — not "was *this specific game* created with the global session." A
player who authorizes globally *after* creating a game the old way (or any
other ordering edge case) would have this pick the wrong key and fail
on-chain with `FeePayerMismatch`. This needs to be tracked per-game, not
read live off wallet state, regardless of which fix path below is chosen.

A third, unrelated gap surfaced when explaining the end-to-end UX: the wallet
**connect** step itself isn't silent either. `provider.connect()` in the
wallet-ui ([App.tsx:502](../../tauri/wallet-ui/src/App.tsx#L502),
[App.tsx:844](../../tauri/wallet-ui/src/App.tsx#L844)) never passes
`{ onlyIfTrusted: true }`, and there's no eager/silent-reconnect attempt
anywhere in that file — so Phantom's own connection-approval popup likely
fires on **every app launch**, not once ever. This is independent of
everything else in this doc (it's in the wallet-ui, not the game client or
backend) but belongs in the same "how many popups does a player actually
see" picture.

## Fix plan (implemented)

Three independent tracks — Track 0 and Track 1 needed no on-chain changes; Track 2 did.

### Track 0 — silent wallet reconnect ✅

Both `provider.connect()` call sites in `App.tsx`
([:502](../../tauri/wallet-ui/src/App.tsx#L502),
[:844](../../tauri/wallet-ui/src/App.tsx#L844)) now try
`connect({ onlyIfTrusted: true })` first, falling back to a plain `connect()`
(the real approval popup) only if that throws — first-ever connection, or
the user revoked access.

### Track 1 — backend awareness of global sessions ✅

1. **Registration**: `establish_global_session` (client) now calls
   `register_global_session_with_backend` after signing on-chain
   ([integration/systems.rs](../../src/multiplayer/solana/integration/systems.rs))
   — hits the new `POST /global-session/register`
   ([global_session.rs](../../backend/src/signing/routes/global_session.rs)),
   which verifies the submitted key against the on-chain
   `GlobalSessionDelegation.session_key` before trusting it (not blind
   trust). Re-registered on every wallet connect too, not just the first
   time, since the backend's `active_global_sessions` map is in-memory only
   and forgets everything on restart.
2. **Signer resolution**: `resolve_game_signer` (backend `main.rs`) — tries
   `SessionStore` first, falls back to reading the Game PDA's `fee_payer`
   on-chain and matching it against `active_global_sessions`. Used by
   `finalize_game`, `undelegate_game`, and `session_status`.
3. **Settlement discovery**: rather than teaching `settlement_worker` a
   second discovery source, global-flow games now get a real `SessionStore`
   row too — `POST /global-session/track-game` calls the new
   `SessionStore::create_with_keypair` ([session.rs](../../backend/src/signing/storage/session.rs))
   with `active=1` immediately. `settlement_worker`'s existing
   `WHERE active = 1` scan just picks these up, unchanged.
4. **Delegation gating bug**: fixed — `EphemeralRollupManager` gained a
   `used_global_session` field, set once at create/join time (via
   `SolanaLobbyState::last_attempt_used_global_session`, captured at the
   moment the transaction is spawned) and read at delegation time instead
   of the live `global_session_active` flag.

### Track 2 — `global_record_move` ✅ (program not yet deployed)

New instruction, [moves_ix/global_record.rs](../../programs/xfchess-game/src/moves_ix/global_record.rs)
— identical to `record_move` except its `session_delegation` account is a
`GlobalSessionDelegation` (seeds `[b"global_session", wallet]`) instead of a
per-game one, with an explicit check that the wallet is actually `game.white`
or `game.black` (a global session isn't scoped to one game the way a
per-game one is, so that has to be checked here instead of being implicit in
the PDA seeds). Move-application logic is shared via `apply::apply_recorded_move`,
unchanged.

Backend: `sessions.is_global` (migration 026) marks which flow a row came
from; `record_move`'s handler branches on it to build either
`record_move_ix` or the new `global_record_move_ix`
([instructions.rs](../../backend/src/signing/solana/instructions.rs)).

## Implementation status

- All three tracks are implemented and each crate (`xfchess` client,
  `backend`, `xfchess-game` program) compiles clean on its own.
- **One thing type-checking can't verify**: the account order/count in
  `global_record_move_ix` (backend, hand-encoded bytes) must exactly match
  `GlobalRecordMove` (program, Anchor-derived) — there's no shared type
  linking them, same as every other hand-rolled instruction builder in this
  codebase already. Cross-checked by hand against the program source; not
  compiler-verified.
- **Not yet done**: deploying the updated program to devnet
  (`scripts\build_program.bat` / `anchor deploy`) — that's a live-program
  change, held back for explicit confirmation before running rather than
  done as part of this pass. Nothing in Track 2 takes effect on live devnet
  games until that happens; Tracks 0 and 1 are already live as soon as the
  backend is redeployed.
- **Not tested against a live app** — only `cargo check` across all crates.
  First real devnet run may still surface something the type checker can't
  catch.
