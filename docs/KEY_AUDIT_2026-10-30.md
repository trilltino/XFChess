# XFChess keys and controls audit — 30 October 2026

This audit covers keyboard bindings, mouse combinations, wallet and network signers, backend credentials, public addresses, and the local configuration files in this checkout. It traces the implementation rather than relying on labels in the UI or examples.

No credentials were changed, no transactions were submitted, and no private values are included here. This is a source and local-configuration audit: the running VPS, deployed program binary, live delegations, provider dashboards, and operating-system credential stores were not inspected. A production-named file in this checkout does not establish the VPS's current configuration.

## Findings that need attention

| ID | Priority | Finding and effect | Evidence / action |
| --- | --- | --- | --- |
| S1 | High | **Quick-sign storage has no secret encryption key.** The AES key is SHA-256 of the public wallet address. Anyone with the saved file and wallet address can decrypt the delegated private key. A constant GCM nonce is also reused across saves for that wallet. | `src/multiplayer/solana/global_session_manager.rs:130–188`. Store the delegated key in the OS credential store or protect it with a random key held there; use a fresh nonce for every encryption. Migrate or invalidate existing saved sessions. |
| S2 | High if still authorized anywhere | **Tracked JavaScript contains two complete private keypairs.** `convert_keys.js` embeds and prints VPS/KYC key material. Both arrays are valid Ed25519 keypairs, but neither matches the current devnet authority constant. This does not establish exposure of the current authority keys. | `services/backend/src/bin/convert_keys.js:20–24`. Remove embedded material, identify any accounts or deployments that still trust those public keys, and retire those authorizations. Removal does not erase previous copies. The Rust converter also deliberately prints private key material; avoid capturing its output in logs. |
| S3 | High for deployment readiness | **The local configurations do not satisfy current production requirements.** Root/backend env files lack `LINK_AUTHORITY_KEY` and have a 12-character admin key; `infra/ops/backend/.env.production` explicitly selects production but lacks required admin/link configuration and has unusable authority/fee-payer entries. | `services/backend/src/signing/config.rs:93–182`; details below. Reconcile configuration before deployment. No conclusion is made about the live VPS. |
| S4 | Medium | **Quick-sign registration omits authentication.** The client creates a fresh HTTP client and posts the session secret without a bearer token. The backend mounts registration behind authentication and requires `RequireWallet`. With the current router, this request is rejected with 401. | `src/multiplayer/solana/integration/systems/global_session.rs:397–414`; `services/backend/src/signing/routes/global_session.rs:37–43`; `services/backend/src/signing/mod.rs` global-session routing. Use the authenticated backend client. Both current registration callers use this helper. |
| S5 | Medium | **Changing authority fields in ProgramConfig does not rotate the privileged roles currently checked against compiled constants.** Updating the env secret or config account alone can leave old authority keys effective and new keys unusable. | `programs/xfchess-game/src/account_ix/config_ix.rs:108–123` versus `constants.rs` and the KYC, treasury, dispute, link and VPS instruction constraints. Plan rotation against the actual deployed program and its upgrade authority. |
| S6 | Medium, conditional on existing data | **Old plaintext session rows remain supported without an automatic rewrite.** New writes use encryption, but a legacy 64-byte keypair is returned directly if decryption fails. Reading an old row does not migrate it. | `services/backend/src/signing/storage/session.rs:453–460`. Check existing databases and retained backups, then migrate legacy rows before claiming all session keys are encrypted at rest. No live database was examined. |
| S7 | Low | **The rotation endpoint generates a candidate but records it as rotated.** It returns a new `ADMIN_API_KEY` candidate without installing it; its audit event calls it `admin_token`, which is also the name of a separate credential. | `services/backend/src/signing/routes/admin.rs:1689–1698`. The response and current Settings UI explain the restart step. Make the audit entry say a replacement was generated, and distinguish the admin API key from `ADMIN_TOKEN`. |
| K1 | Medium | **Ctrl+B triggers two actions.** The unmodified B handler also accepts Ctrl+B, so the chord toggles both HUD visibility and blindfold mode. | `src/ui/game/game_ui/mod.rs:39–45,285–293`; both systems are chained in `src/game/plugin.rs:185–188`. Exclude modifiers from the plain-B action. |
| K2 | Medium | **Up/Down navigation is reversed for Black in the 2D board.** Horizontal keys account for Black's orientation; vertical keys do not. In Black view, increasing rank increases screen Y, so Up moves the focus down. | `src/ui/game/game_2d/render.rs:708–723`; `src/ui/game/game_2d/mod.rs:53–61`. Mirror the rank step for Black. |
| K3 | Low | **The Controls popup describes unimplemented or different bindings.** It advertises F to flip, U to undo and middle-drag to orbit. No F/U keyboard handlers were found; desktop rotation uses right-drag. Escape opens exit confirmation rather than pausing the game. | `src/states/main_menu/modals.rs:254–263`; `src/game/systems/camera.rs:160–216`; `src/input/board.rs:893–910`. Replace the help text with the implemented controls below. |
| K4 | Low | **Numpad Enter is inconsistent.** It acknowledges the finished-game prompt, but does not activate a square in 2D keyboard navigation. | `src/game/systems/game_logic.rs:246`; `src/ui/game/game_2d/render.rs:725`. Accept Numpad Enter in the board action if equivalent behavior is intended. |

## Wallet, session and network keys

| Key / signer | Owner and storage | What it authorizes / what losing it means |
| --- | --- | --- |
| Player's external or Privy wallet key | Wallet provider. XFChess receives public addresses and signing responses. | Wallet transactions and signed login/identity proofs. The normal provider flow does not send the main wallet private key to the backend. |
| Local hot-wallet key | Game, `hot_wallet.json` or `hot_wallet_<port>.json` in its platform config directory. Created as plaintext JSON; Unix creation uses mode 0600. | Full control of that generated wallet and its funds. Windows relies on directory/file ACLs; those ACLs were not audited. Keep separate from limited session signers. |
| Backend per-game session key | Generated by `SessionStore::create`; stored in the sessions database. Shared per game in the classic flow. New rows are encrypted with `IDENTITY_ENCRYPTION_KEY`. | Signs backend game/rollup operations permitted by the on-chain delegation, avoiding repeated wallet prompts. Backend has the private key. The per-game `authorize_session_key` instruction sets a two-hour authorization and maximum batch length of 10. |
| Global quick-sign session key | Generated on the client; saved as `global_session_key.enc`; sent privately to the backend registration endpoint; held in memory and copied into encrypted game-session rows when tracked. | Delegated game creation/joining and associated game operations within the on-chain budget, expiry and game count. Program defaults: 30 days, 200 games, 5 SOL aggregate spending limit, 1 SOL maximum wager; callers can provide other permitted settings. The delegation's deposited funds and signed scope, not the entire main wallet, are exposed if this key is stolen. S1 and S4 apply. |
| Generic `PlayerSession` signer | On-chain session authorization created by `create_session`; not a distinct backend env key. | Permissions include creating/joining games and claiming prizes. Defaults: 24 hours, 0.5 SOL total spending, 10 SOL per-wager ceiling; the total budget can be more restrictive than the per-wager ceiling. |
| Tournament-session signer | On-chain tournament/player-specific delegation; distinct from the backend's shared per-game session. | Tournament-scoped delegated operations. Program defaults: 48 hours, 1 SOL total spending, 0.25 SOL maximum wager. Current backend tournament game endpoints create/reuse per-game session keys; no separate tournament private-key env variable was found. |
| Wallet gossip signer | Client, random 32-byte seed in `gossip_seed_<wallet>` under its config directory. | Authenticates game/network messages. It is separate from the funds-authorizing delegation key. Stored as plaintext bytes using ordinary file creation. |
| Persistent node identity | Client, 32-byte `node_key`; override path via `XFCHESS_NODE_KEY_PATH`, or mesh override `XFCHESS_IDENTITY`. Secondary instances can use a temporary identity. | Iroh network identity and node-auth proofs. Casual play also uses it for message signing when no wallet is connected. Theft enables node impersonation, not automatic access to a player's wallet. |
| `X-Node-Auth` token | Short-lived self-signed proof produced from the node identity; cached in memory. | Proves possession of the node private key to wallet-free services, including casual-game, social and lobby operations. It is not signed using `JWT_SECRET`. |
| `HandshakeOrderingKeyManager` key | Helper can persist raw 64-byte keys to `session_keys/game_<id>.key`; Unix permission tightening occurs after writing. | Used by handshake/session-ordering machinery. Resource initialization and public-key reads are present, but no non-test caller of its key-creation methods was found; do not assume it is the active gameplay signer. |
| Legacy launcher `GameSession.session_signer_secret` | Loaded from `XFCHESS_SESSION_DATA`, `XFCHESS_SESSION_FILE`, or newest valid `xfchess_session_*.json` in the temp directory. | Supplies a session signer to the Solana session plugin. It is private material even though it arrives as JSON. The loader validates signer/public-key agreement and expiry. |

Primary sources: `src/multiplayer/solana/integration/systems/wallet.rs:172–258`, `services/backend/src/signing/storage/session.rs:319–460`, `src/multiplayer/solana/global_session_manager.rs`, `src/multiplayer/network/device_id.rs:76–101`, `src/multiplayer/network/identity.rs`, `src/multiplayer/systems/mesh.rs:431–470`, `services/backend/src/signing/node_auth.rs`, `src/solana/session/mod.rs`, and the program's session state/instruction modules.

**Revocation has multiple layers.** Deleting the backend's global-session registration removes its in-memory entry; that endpoint explicitly does not revoke the on-chain delegation. Keys already copied into game-session rows are separate persisted copies. Expiry/revocation on chain determines whether delegated transactions remain authorized. Do not treat logout, deleting a local file, or the backend DELETE endpoint as proof that all delegated signing authority has been revoked.

Never place privileged provider secrets into public frontend build variables. |

`PROGRAM_ID`, `USDC_MINT`, `TOURNAMENT_FEE_RECIPIENT`, the treasury public key and program-derived addresses are public identifiers. `HOST_TREASURY_PUBKEY` is present in local env files but has no current source consumer found; the backend reads `TOURNAMENT_FEE_RECIPIENT`. Program-derived addresses do not have a corresponding stored private key: the program controls their authorized signing behavior.

**Normal authorization flow:** the player's wallet signs a login challenge; the backend verifies ownership and issues a JWT. Wallet-specific HTTP operations use that JWT. The wallet separately authorizes a session public key on chain. The backend or client holding that delegated private key can then perform permitted operations, with the fee payer covering transaction costs. Network/node signatures prove message origin and are a separate layer.

## Verification and limits

- Enumerated `KeyCode`, egui key handling and browser keyboard-event patterns across the game, backend and frontends; followed system registration and state conditions.
- Read env values in memory to report redacted metadata only; checked keypair validity by deriving the Ed25519 public key and comparing it to the supplied public half and source devnet constants.
- Reproduced quick-sign decryption with a synthetic session secret and only a generated public wallet address. It recovered the plaintext, confirming S1 without decrypting a real player's session.
- Validated the two embedded JavaScript keypairs and confirmed neither matches the current source devnet constant for its named role. Did not execute the conversion utilities.
- Checked the 2D coordinate mapping: Black view maps rank 3 to screen row 3 and the Up handler changes it to row 4, confirming downward movement.
- No application code was changed and no full game/backend build, live GUI test, database migration, external-provider authentication or on-chain transaction was run.

Suggested order: protect quick-sign key storage and address the embedded exposed key material; fix authenticated registration; reconcile production configuration and rotation procedures; then fix the keyboard conflicts, Black-view navigation and Controls popup.
